## 1. 迁移结论

后端迁移目标为：

> **模块化单体（Modular Monolith）+ 业务域纵向组织 + 模块内轻量分层**

不采用微服务，也不为每个模块强行增加 Domain、Port、Adapter、Factory 等抽象层。

当前项目已经形成 `backend-fastapi/app/main.py` 作为运行入口，因此第一阶段保留 `app` 根包，只增加 `app/modules/` 并逐模块迁移。暂不将项目改为 `src/` 布局，避免同时改变启动脚本、导入路径和部署方式。

未来如果重新创建后端，再考虑使用：

```text
backend-fastapi/src/web408/
```

## 2. 当前基线与已确认事实

### 2.1 运行与公开契约

- Python 要求为 `>=3.12`。
- 依赖使用 FastAPI、SQLModel、aiosqlite、Pydantic 2、pydantic-settings、JWT 和 aiofiles。
- 启动入口为 `app.main:app`。
- 数据库为本地 SQLite，默认路径为 `backend-fastapi/data/web408.db`。
- 图片默认保存在 `backend-fastapi/uploads/images/`。
- API 前缀为 `/api`。
- Web API 当前统一使用 POST。
- 成功响应使用 `{code, message, data}`。
- 分页数据使用 `lists` 和 `pagination`。
- 当前数据库初始化使用 SQLModel `create_all`，没有迁移链。
- 迁移开始前发现当前数据库与 Git 版本存在未提交数据差异；当前 `mock_question` 为 246 条，Git 版本为 232 条。经确认保留当前数据库作为迁移基线，不覆盖、不回滚、不清理。

### 2.2 当前代码组织

当前结构是横向分层：

```text
app/
├── api/
├── core/
├── database/
├── middleware/
├── models/
├── repositories/
├── schemas/
└── services/
```

当前已经存在查询 Service、命令 Service 和兼容门面 Service，但业务文件仍然分散在多个顶层目录中。修改一个业务通常需要同时定位 API、Schema、Model、Repository 和多个 Service 文件。

### 2.3 迁移前需要处理的结构问题

1. `ExamService`、`MockService`、`ExamCategoryService` 主要是转发包装层，增加了调用跳转。
2. `ExamCommandService` 依赖 `ExamQueryService`，分类命令 Service 依赖分类查询 Service，查询和写入边界不够清晰。
3. `models/entities.py` 混合了用户、目录、真题、模拟题、资源和未形成业务闭环的模型。
4. `exam_query_service.py`、`exam_export_service.py`、`category_query_service.py` 等文件同时承担多个变化原因。
5. 真题和模拟题的题目选项、分类序列化及题目校验集中在全局 `services/`，但实际只服务于题库内容域。
6. `ExamQuestion.category` 和 `MockQuestion.category` 当前以分类名称 JSON 字符串保存，查询依赖字符串匹配，统计需要在内存解析。
7. 当前响应转换会逐条读取科目和作者，存在 N+1 查询风险。
8. 当前后端源码中未发现 `KnowledgePoint`、`ExamRandomStat`、`ResourceFile` 被路由或业务 Service 使用；迁移时应先隔离，不直接当作核心模块继续扩展。
9. `exam_query_service.py` 的 `get_categories_by_subject()` 曾缺少 `json` 导入；当前代码已修复，后续不再作为未解决问题追踪。

## 3. 迁移原则

### 3.1 公开行为不变

第一阶段只调整内部结构，不改变：

- API URL、HTTP 方法和响应字段；
- 前端当前使用的请求参数和字段命名；
- 数据库表名、字段名和现有约束；
- 图片持久化相对路径规则；
- JWT 登录和管理员权限行为。

顶层 `app/api/router.py` 继续作为路由组合入口，通过新的模块路由注册现有前缀，例如 `/auth`、`/subject`、`/exam`、`/mock` 和 `/upload`。

### 3.2 单向依赖

```text
Router
  ↓
Query Service / Command Service
  ↓
Repository / 其他模块公开 Service / Storage
  ↓
Database / 文件系统
```

必须遵守：

- Router 不直接查询数据库或提交事务。
- Schema 不查询数据库、不判断权限、不调用外部服务。
- Repository 不调用 Service，不提交或回滚事务。
- Command Service 或跨模块 Workflow 拥有事务边界。
- 模块之间不得直接引用对方的 Repository 或私有实现。
- 统计、媒体和题库之间的跨模块读取统一通过公开 Service 和只读 DTO。
- `ExamQuestion` 与 `MockQuestion` 保持独立实体，只共享题目内容规则、序列化和校验。
- `core/` 和 `database/` 不依赖业务模块。
- 不创建没有实际职责的空文件和空目录。
- 不创建万能 `common/utils.py`、通用 Repository 基类或过早的接口层。

### 3.3 事务与异常

- 一个业务用例对应一个事务边界。
- 写入 Service 使用显式事务，Repository 只执行持久化操作。
- 查询 Service 不提交事务。
- 业务异常由全局异常处理器统一映射，路由不重复编写相同的 `try/except`。
- 文件写入使用临时文件和原子替换；文件系统操作失败时清理临时文件。

## 7. 统计、媒体与跨模块协作

### 7.1 统计与导出

统计和导出虽然当前部分路由位于 `/exam`，实现上应归属 `reporting`：

- `exam` 提供题目读取能力；
- `catalog` 提供分类树和目录顺序；
- `reporting` 负责分类统计、去重口径和导出格式；
- 为兼容前端，原有 `/api/exam/category-stats` 和 `/api/exam/export-category-stats` 路径可以继续由组合路由注册。

统计规则保持现有文档定义：题目 ID 去重数、分类引用数、章节子树汇总数和未归档分类分别表达。

### 7.2 图片资源

将当前 `UploadService` 拆为三个职责：

1. `media/service.py`：上传、删除、清理等业务用例；
2. `integrations/local_file_storage.py`：安全路径、临时文件、原子替换和文件读写；
3. `media/reference_reader.py`：读取真题和模拟题文本并判断引用关系。

媒体模块不得直接修改题目内容，也不得把图片删除结果当成题目更新操作。

## 8. 数据库迁移策略

### 8.1 第一阶段：只重组代码

- 保留现有表名、字段名、外键和唯一约束。
- 保留题目选项和分类 JSON 存储格式。
- 只拆分 Model 文件和 Repository 所属位置。
- 不删除、覆盖或重建现有数据库。
- 不创建数据库迁移链。

### 8.2 第二阶段：可选的数据模型改造

长期建议将分类名称 JSON 改为关联表：

```text
exam_question_category(question_id, category_id)
mock_question_category(mock_id, category_id)
```

收益：

- 分类改名不会产生字符串孤立引用；
- 可以使用外键约束；
- 分类统计可直接使用 JOIN 和聚合；
- 不再依赖 JSON 字符串 `LIKE` 查询。

该改造会改变数据库结构，必须单独编写数据方案。实际删除或重建数据库前，需要明确数据库绝对路径、数据损失范围、重建方式和检查方式，并获得用户授权。

## 9. 分阶段执行计划

| 阶段 | 目标 | 主要范围 | 前置条件 | 优先级/规模 | 验收与回滚 |
|---|---|---|---|---|---|

### 9.1 提交和回滚规则

- 每个业务模块独立提交，避免一次提交同时移动所有目录。
- 先移动代码并保持旧 API，再删除旧门面和旧目录。
- 仓库内所有导入在对应阶段一次性更新，不保留旧 `app.services`、`app.repositories` 等内部兼容别名。
- 第一阶段只修复阻塞迁移或确定性运行错误，例如缺失的 `json` 导入；N+1 和其他性能优化另列后续任务。
- 第一阶段不修改数据库结构，代码迁移失败时直接回退对应提交。
- 数据库结构改造与代码模块迁移不得放在同一阶段执行。

## 10. 验收标准

### 10.1 结构验收

- 业务代码位于对应模块，不再从全局 `services/`、`repositories/` 查找所有业务。
- Repository 不包含 `commit()`、`rollback()` 或 HTTP 异常。
- Schema 不执行 I/O 或数据库查询。
- 模块之间没有反向私有导入和循环依赖。
- 跨模块读取只使用公开 Service 和只读 DTO。
- 应用启动阶段显式注册全部需要保留的 SQLModel 模型。
- 不存在仅用于目录对称的空文件。

### 10.2 行为验收

- 现有 API URL、POST 方法和响应信封保持不变。
- 登录、管理员权限、分类树、真题、模拟题、统计、导出和图片功能行为保持不变。
- 分类统计继续区分去重题目数和分类引用数。
- 图片仍使用 `/uploads/images/{filename}` 相对路径。
- 题型校验、重复校验和历史分类处理规则不被迁移过程改变。

### 10.3 质量验收

- 已修复 `json` 导入问题；继续修复其他阻塞迁移的确定性错误。
- 大型文件按独立变化原因拆分，不为减少文件数量重新合并。
- 关键查询、写入和异常边界完成人工核对。
- N+1 查询和其他性能优化不作为首轮迁移验收项，迁移完成后单独评估。
